# Counters

Небольшой HTTPS-сервис для именованных целочисленных счётчиков: создать, прочитать, увеличить на
единицу, удалить. По сути `Map<String, Int>`, только с персистентностью в PostgreSQL, защитой от
повторов через `Idempotency-Key` и корректной работой под конкурентной нагрузкой.

Kotlin 2.0, Ktor 3, kotlinx.serialization, JetBrains Exposed, PostgreSQL 16, Liquibase, HikariCP.
Нужен JDK 21.

## Запуск

Нужен PostgreSQL. Если своего нет — в репозитории лежит `docker-compose.yml`:

```bash
docker compose up -d      # PostgreSQL 16 на localhost:5432, postgres/root
./gradlew run             # https://localhost:8443
```

При первом запуске приложение создаст схему `counters` и накатит миграции. Сервис слушает только
HTTPS: самоподписанный сертификат (`CN=localhost`) генерирует Gradle-задача `generateDevKeystore`
в `keystore.p12` в корне проекта, а `exportDevCertificate` выгружает его публичную часть рядом в
`counters.crt`; обе задачи — зависимости `run`, оба файла в `.gitignore`. Для не-локального
окружения хранилище с настоящим сертификатом подставляется через переменные `KEYSTORE_*`.

Swagger UI: <https://localhost:8443/swagger>. Сертификат самоподписанный, так что браузер один раз
спросит, доверять ли ему; `curl` — либо с `--cacert counters.crt`, либо с `-k`.

```bash
KEY=$(uuidgen)   # Windows: powershell -c "[guid]::NewGuid().ToString()"

curl --cacert counters.crt -X POST https://localhost:8443/counters \
  -H 'Content-Type: application/json' -H "Idempotency-Key: $KEY" \
  -d '{"name":"page-views","initialValue":0}'

curl --cacert counters.crt -X POST https://localhost:8443/counters/page-views/increment \
  -H "Idempotency-Key: $(uuidgen)"

curl --cacert counters.crt https://localhost:8443/counters/page-views
curl --cacert counters.crt https://localhost:8443/counters
curl --cacert counters.crt -X DELETE https://localhost:8443/counters/page-views
```

## API

| Метод | Путь | Запрос | Успех | Ошибки |
|---|---|---|---|---|
| `POST` | `/counters` | заголовок `Idempotency-Key: <uuid>`; тело `{"name": string, "initialValue": int = 0}` | `201`, заголовок `Location: /counters/{name}`, тело `{"name","value"}` | `400`, `409`, `422`, `500` |
| `GET` | `/counters` | — | `200`, массив `{"name","value"}` по имени | `500` |
| `GET` | `/counters/{name}` | — | `200`, `{"name","value"}` | `400`, `404`, `500` |
| `DELETE` | `/counters/{name}` | — | `204` | `400`, `404`, `500` |
| `POST` | `/counters/{name}/increment` | заголовок `Idempotency-Key: <uuid>` | `200`, `{"name","value"}` с новым значением | `400`, `404`, `409`, `422`, `500` |

```jsonc
{ "name": "page-views", "initialValue": 0 }   // создание; initialValue можно опустить
{ "name": "page-views", "value": 42 }         // счётчик — в ответах create / get / list / increment
{ "error": "counter 'page-views' not found" } // любая ошибка
```

Имя — от 1 до 255 символов из `[A-Za-z0-9_.-]`, одинаково для тела и для сегмента `{name}` в пути.
Так имя всегда можно подставить в URL как есть, без кодирования и без вопросов про регистр и
пробелы. Полная спецификация — `src/main/resources/openapi/documentation.yaml`.

### Коды ответов

| Код | Когда |
|---|---|
| `200` | чтение; инкремент (ничего не создаётся) |
| `201` | счётчик создан, в `Location` — его адрес. Повтор с тем же ключом вернёт тот же `201` |
| `204` | счётчик удалён |
| `400` | битый JSON или нет обязательного поля; невалидное имя в теле или пути; нет заголовка `Idempotency-Key` или это не UUID |
| `404` | нет такого счётчика (или он удалён) — для `GET`, `DELETE`, `increment` |
| `409` | счётчик с таким именем уже есть; счётчик упёрся в `Int.MAX_VALUE`; запрос с этим `Idempotency-Key` ещё выполняется |
| `422` | `Idempotency-Key` уже использован для *другого* запроса — другое имя или другая операция |
| `500` | что-то пошло не так на сервере (например, недоступна БД). Тело — тот же `{"error"}`, без стек-трейсов |

## Почему так

**Создание — `POST /counters`, а не `PUT /counters/{name}`.** `PUT` идемпотентен из коробки, но
означает «создать или заменить». Мне же нужно, чтобы повторное создание существующего счётчика
было ошибкой, а при гонке создания с одним именем выигрывал ровно один запрос — затирать живой
счётчик нельзя. Поэтому `POST`, `409` на дубликат, а безопасность повторов даёт `Idempotency-Key`.

**Дубликат — `409`, а не `200` с данными существующего.** Ответить `200` на
`{name, initialValue}` и вернуть чужое значение — это код успеха для запроса, который не выполнен.
И при гонке создания все запросы «успевали» бы, что противоречит цели.

**Инкремент — `POST /counters/{name}/increment`.** Это действие, не идемпотентное по природе:
каждый вызов меняет состояние. Отсюда `POST` на под-ресурс, а повторы делает безопасными ключ.

**`GET`** безопасны и идемпотентны. **`DELETE`** идемпотентен по эффекту: второй вызов ничего не
меняет и отвечает `404`, потому что ресурса уже нет.

**`409` против `422` для ключей.** «Ключ ещё выполняется» (`409`) и «ключ переиспользован с другим
запросом» (`422`) разведены так, как это делает IETF-драфт *The Idempotency-Key HTTP Header
Field*: клиент различает случаи по коду, без разбора текста.

**Soft delete.** `DELETE` выставляет `is_deleted = true`, а не удаляет строку: история остаётся,
удалённые счётчики для API невидимы. Уникальность имени действует только среди живых
(частичный уникальный индекс), поэтому удалённое имя можно занять заново — это будет новый
счётчик с `initialValue`, а не воскрешение старого.

**Миграции — Liquibase formatted SQL.** Обычный DDL с `--changeset`-маркерами
(`src/main/resources/db/changelog/db.changelog-master.sql`). Сервис привязан к PostgreSQL —
частичный индекс, `jsonb`, `ON CONFLICT`, `RETURNING` — и абстрактные change-типы Liquibase
частичный индекс всё равно не выражают. Плоский SQL показывает ровно то, что выполнится.
Changeset'ы только добавляются, существующие не редактируются.

**Exposed без ORM-слоя.** Чтения написаны на Exposed DSL. Три изменяющих выражения — создание,
инкремент, удаление — это raw SQL через `Transaction.exec`, потому что им нужны `RETURNING` и
`ON CONFLICT` по частичному индексу, а их точная форма и есть аргумент про конкурентность (ниже).
Модель ORM «загрузить сущность — изменить — сбросить» — та самая гонка чтения-записи, которой
здесь быть не должно.

## Конкурентный доступ

Инкремент — одно атомарное выражение:

```sql
UPDATE counters SET value = value + 1, updated_at = now()
WHERE name = ? AND NOT is_deleted AND value < 2147483647
RETURNING id, name, value, is_deleted, created_at, updated_at
```

PostgreSQL упорядочивает конкурентные обновления одной строки блокировкой строки: N параллельных
инкрементов ложатся как N отдельных `+1`, итог — ровно `+N`, и каждый вызов получает своё
уникальное значение. Чтения «прочитать-изменить-записать» в коде нет вообще. Условие
`value < Int.MAX_VALUE` не даёт переполнению вылиться в SQL-ошибку (она прервала бы транзакцию,
общую с записью идемпотентности); если строка не обновилась, отдельный `SELECT` различает «нет
счётчика» (`404`) и «достигнут максимум» (`409`).

Создание — `INSERT … ON CONFLICT (name) WHERE NOT is_deleted DO NOTHING RETURNING …` поверх
частичного уникального индекса. При гонке создания одноимённых счётчиков строку вставляет ровно
один запрос, остальные получают `409`. `ON CONFLICT` вместо перехвата исключения — по той же
причине: упавший `INSERT` прервал бы общую транзакцию.

## Идемпотентность

Клиент генерирует UUID до первого запроса и повторяет его во всех ретраях этого запроса; для
новой операции — новый ключ. На сервере ключ — это строка в таблице `idempotency_keys`, и вся
логика строится на одном принципе: сначала занять ключ, потом разбираться. Проверка «есть ли уже
такой ключ» отдельным запросом не подходит — два одновременных запроса оба увидят пустоту и оба
выполнят операцию. Поэтому:

1. `INSERT … ON CONFLICT (key) DO NOTHING RETURNING key` атомарно занимает ключ в состоянии
   `processing`. База гарантирует, что из конкурентных запросов с одним ключом строку вставит
   ровно один — он и выполняет операцию.
2. Все остальные видят, что вставка не прошла, и читают уже существующую строку:
   - `request_hash` не совпадает → `422`, ключ уже использован для другого запроса;
   - `state = completed` → replay: отдаём сохранённые `response_code` и `response_body`, ничего не
     выполняя — в том числе для `409` и `404`, исход фиксируется любой;
   - `state = processing` → `409`, запрос ещё в работе.
3. Операция над счётчиком и запись результата коммитятся **в одной транзакции**. Состояния
   «инкремент применён, но не записан» не бывает: если процесс упал, откатывается всё.
4. Строка `processing` старше 60 секунд считается брошенной — процесс упал между шагами. Её
   атомарно перехватывает следующий запрос с тем же ключом и выполняет операцию заново; это
   безопасно благодаря пункту 3.
5. Детерминированные исходы — `201`, `200`, `404`, `409` — записываются и воспроизводятся.
   Исключение во время операции (упала БД, кончился пул) означает, что транзакция откатилась и
   ничего не произошло: резервирование снимается, и повтор с тем же ключом выполняет операцию
   заново, а не получает замороженный навечно `500`.

`request_hash` — это операция плюс имя: `create:<name>` или `increment:<name>`. Ключ
идентифицирует операцию, а не точное тело: повтор с тем же ключом и именем, но другим
`initialValue`, считается тем же запросом и получает replay. А вот ключ от создания на
инкременте того же счётчика даст `422` — иначе инкремент воспроизвёл бы ответ создания.

Известное ограничение: перехват брошенного ключа (п. 4) не защищён от медленного, но живого
исходного запроса. Если тот доживёт до конца после 60 секунд, операция выполнится дважды. Для
операций в миллисекунды это требует патологической паузы — GC на минуту, разрыв сети до БД.
Лечится токеном владения (`attempt`) в строке ключа с проверкой при записи результата; пока не
делал. Очистку старых ключей тоже не делал.

## Тесты

```bash
./gradlew test
```

По умолчанию тесты поднимают одноразовый PostgreSQL через Testcontainers — нужен Docker. Без Docker
можно указать существующий инстанс; тесты работают в отдельной схеме `counters_test` и данные
разработки не трогают:

```bash
TEST_DATABASE_URL=jdbc:postgresql://localhost:5432/postgres \
TEST_DATABASE_USER=postgres TEST_DATABASE_PASSWORD=root ./gradlew test
```

Стиль кода проверяет ktlint (`./gradlew ktlintCheck`, автоисправление — `ktlintFormat`), входит в
`check`; правила — в `.editorconfig`, максимум 120 символов в строке.

Тесты поднимают настоящий модуль приложения (`testApplication`) и ходят в него Ktor-клиентом —
через маршруты, сервисы, Exposed, миграции и реальный PostgreSQL, тем же путём, что внешний
клиент. `HttpsTest` собирает сервер так же, как `EngineMain` (`CommandLineConfig` +
`application.conf`), на случайном порту, и проверяет TLS через настоящий сокет.

| Класс | Что проверяет |
|---|---|
| `ConcurrencyTest` | 200 параллельных инкрементов дают ровно +200, и все 200 ответов содержат разные значения; 50 параллельных созданий одного имени — один `201`, остальные `409`; 20 параллельных повторов с одним ключом двигают счётчик один раз |
| `IdempotencyTest` | replay `201`/`200`/`409` по тому же ключу без повторного выполнения; `422` при переиспользовании ключа с другим именем и с другой операцией; `409` для ключа в `processing`; перехват брошенного ключа старше 60 с — операция выполняется ровно один раз |
| `CountersApiTest` | все операции и коды: `201` + `Location`, `200`, `204`, `400` (тело, имя в теле и в пути, заголовок), `404`, `409` (дубликат, переполнение `Int.MAX_VALUE` и его replay); soft delete и повторное создание имени |
| `FacadeFailureTest` | исключение внутри операции снимает резервирование ключа, и повтор с тем же ключом выполняется |
| `PersistenceTest` | значения переживают перезапуск приложения — новый инстанс, тот же PostgreSQL |
| `HttpsTest` | открыт ровно один коннектор и он HTTPS; клиент с нашим сертификатом получает `200`; клиент с системным доверием не проходит рукопожатие; plaintext на TLS-порт отклоняется |
